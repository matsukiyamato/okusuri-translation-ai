### データべース構造定義・詳細設計書
本ドキュメントは、医療情報アクセシビリティ支援システム「お薬翻訳AI」において使用する関係データベース（MySQL）およびベクトルデータベース（ChromaDB）のデータ構造、スキーマ、セキュリティ要件、および実機構築用のDDL・コマンドを定義した開発メモである。

### 1. データベース全体アーキテクチャと役割分担

本システムでは、データの性質に応じて2種類のデータベースを使い分ける。

1. **MySQL**（関係データベース）

**役割**: 整合性と機密性が求められるユーザーのアイデンティティ情報、認証ステート、インターフェース選択モードの永続化。

**セキュリティ特徴**: 個人情報（Email）のAES-256-GCM暗号化保存（バイナリ格納）、Argon2idによるパスワードハッシュ化。

2. **ChromaDB**（ベクトルデータベース）

**役割**: 公的医療情報（PMDA等）の「やさしい日本語」変換およびRAG（検索拡張生成）用コンテキストのベクトル検索。

**データ構造**: 各ドキュメントをチャンク（断片）化し、Geminiの埋め込みモデル（Embedding API）で多次元ベクトル化したデータを格納。

### 3. MySQL データベース構築・運用コマンド

## 3.1 データベース・テーブル作成 DDL
```SQL
-- データベースの作成（ユニコード対応）
CREATE DATABASE IF NOT EXISTS okusuri_translation_db
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_bin;

USE okusuri_translation_db;

-- 1. usersテーブルの作成
CREATE TABLE IF NOT EXISTS users (
    id VARCHAR(36) NOT NULL,
    encrypted_email VARBINARY(255) NOT NULL,
    password_hash VARCHAR(255) DEFAULT NULL,
    interface_mode ENUM('TEXT_AUDIO', 'SIGN_LANGUAGE') DEFAULT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uq_encrypted_email (encrypted_email)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_bin;

-- 2. sign_dictionaryテーブルの作成
CREATE TABLE IF NOT EXISTS sign_dictionary (
    id INT AUTO_INCREMENT NOT NULL,
    word VARCHAR(100) NOT NULL,
    video_url VARCHAR(512) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uq_word (word),
    INDEX idx_word (word)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_bin;
```

## 3.2 24時間経過した不完全な仮登録データの自動物理削除クエリ

### 4. ChromaDB (ベクトルデータベース) 構造
ChromaDBはリレーショナルデータベースのような「テーブル」ではなく、「コレクション（Collection）」単位でデータを管理する。RAGシステムにおいて、PMDA公的文書情報および添付文書情報を構造化して埋め込み（Embedding）ベクトルとして格納する。

## 4.1 コレクション定義：pmda_medical_knowledge

**構造概要**
**Embedding Model**: text-embedding-004 (Gemini Embedding API) ➔ 768次元

**Distance Metric**: cosine (コサイン類似度)

**データ構成要素（メタデータ・スキーマ）**
ChromaDBの内部では、id、vector (embeddings)、document (生テキスト)、および条件絞り込み用の metadata が1つのドキュメント単位として構造化される。

| 要素名 | キー名 / 物理表現 | データ型 | 説明 |
| --- | --- | --- | --- |
| 一意キー | id | str | チャンクごとに発行する一意のID (例: doc_pmda_001_chunk_0) |
| ベクトル値 | embeddings | List[float] | Gemini APIを介して生成された768次元の数値配列 |
| チャンクテキスト | document|str | 分割された「やさしい日本語」を含む、医療情報の部分生テキスト |
|メタデータ（辞書型） | metadata |dict | 以下のフィルタリング用属性を内包する |
| └ 医薬品一般名 |medicine_name | str | 例: ロキソプロフェンナトリウム（完全一致検索用） |  
| └ 文書ソースカテゴリ | source_type |str |package_insert（添付文書）, patient_guide（患者向医薬品ガイド） |
|└ 出典元表記テキスト | source_citation | str |画面最下部に表記する「出典：PMDA」等の客観的根拠文字列 |

### 5. ChromaDB 構築・操作コードメモ (Python / FastAPI)
バックエンド層（backend/app/api/rag.py）からChromaDBを初期化・運用するためのPython実装コードメモ。

## 5.1 コレクションの初期化とデータ挿入
```Python
import chromadb
from chromadb.config import Settings

# ChromaDBクライアントの初期化（永続化ディレクトリの指定）
chroma_client = chromadb.PersistentClient(
    path="./chroma_db_storage",
    settings=Settings(allow_reset=True)
)

# コレクションの取得または作成（コサイン類似度を指定）
collection = chroma_client.get_or_create_collection(
    name="pmda_medical_knowledge",
    metadata={"hnsw:space": "cosine"}
)

# データのインサート/アップサート処理の例
def insert_medical_chunk(chunk_id: str, embedding: list, text: str, medicine_name: str, source_type: str):
    collection.upsert(
        ids=[chunk_id],
        embeddings=[embedding],
        documents=[text],
        metadatas=[{
            "medicine_name": medicine_name.strip(),
            "source_type": source_type,
            "source_citation": "独立行政法人 医薬品医療機器総合機構（PMDA）公的データ"
        }]
    )
```

## 5.2 RAG実行時のベクトル検索（クエリ）
```Python
def query_medical_knowledge(query_embedding: list, medicine_name: str, top_k: int = 3):
    # 特定の薬剤名でメタデータフィルタリングを行いつつ、ベクトル類似度検索を実行
    results = collection.query(
        query_embeddings=[query_embedding],
        n_results=top_k,
        where={"medicine_name": medicine_name} # メタデータ完全一致フィルタ
    )
    return results
```
